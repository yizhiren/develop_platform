# 里程碑 7：需求澄清闭环

- 日期：2026-08-05
- 状态：本地完成

## 问题

Agent1 已在 `clarification_spec.open_questions` 中生成问题，但 Web 只显示通用审批框，问题被埋在版本化产物底部。用户填写“要求补充”时，意见仅进入审批和审计记录，没有进入下一轮 Agent1 的任务上下文，因此不构成真正的澄清对话。

## 实现决策

- 需求详情顶部增加专用“与需求澄清者对话”区域，展示 Agent1 摘要、规格版本和逐条待回答问题。
- 用户回答通过 `request_more_clarification` 持久化到 `conversation_messages`，再调度 Agent1。
- 工作流任务上下文增加按时间排序的 `conversation`，同时保留最新版本 `clarification_spec`。
- Agent1 提示词要求吸收历史回答、避免重复已解决问题，并在信息充分时返回空 `open_questions`。
- 存在待回答问题时等待需求提出者回复；问题清零后自动调度系统架构师，不设置重复的人工确认按钮。
- “仅记录讨论”的消息也进入后续 Agent 上下文，但不会立即触发新一轮运行。

## 验证计划

| 验证 | 预期结果 |
| --- | --- |
| 工作流单元测试 | 用户回答被持久化，并出现在下一轮 `agent.clarify` 上下文 |
| 自动流转测试 | 有问题时等待回答；无问题时直接调度方案设计 |
| 前端静态检查与生产构建 | 类型、交互与响应式样式通过 |
| 页面文案测试 | 澄清对话、问题清单和回答按钮不会被后续改动意外移除 |
| 本地容器 | Control Plane 健康，Web 页面正常响应 |
