# 里程碑 17：需求协作泳道与任务交接可视化

- 日期：2026-08-06
- 状态：已实现、部署并完成自动化验证；等待连接浏览器后的截图级验收

## 用户问题

需求详情原先把 AgentRun 逆序显示成单列日志。多轮开发、Code Review 与返工时，相同角色反复出现，长错误文本占据大量空间，无法快速判断当前任务由谁持有，也看不清需求规格、实现方案、代码、Review 意见和验收结果如何在角色间传递。

## 设计

主视图改为纵向时间、横向角色的泳道图，包含六条泳道：

1. 需求方：发布、补充、批准、退回和重试；
2. 需求澄清师：需求澄清与规格输出；
3. 系统架构师：方案设计、方案修订与 Code Review；
4. 开发工程师：编码、测试与返工；
5. 验收工程师：功能验收、组合回归和最终验收；
6. 画板 / Git：工作区、提交、推送、验证与合并。

AgentRun 在 Worker 取得租约后显示为“执行中”，终态使用实际完成时间进入对应泳道；人工状态迁移与关键可信自动化事件从 Timeline 合并进入同一时间轴。Review、验收、组合回归和最终验收的业务结论会与对应 AgentRun 合并展示，避免把“Agent 正常返回驳回结论”误画成绿色成功。相邻事件之间显示方向箭头，并根据角色组合标注“需求说明与补充”“已确认的需求规格”“实现方案与约束”“代码、测试与提交 · Review”“Code Review 意见 · 返工”“验收问题 · 重新设计”等交接语义。

没有 AgentRun 的 Git 与 Dependency 任务在排队和执行期间也进入“画板 / Git”泳道；完成后由持久化 Timeline 事件接替，因此工作区恢复、依赖安装、提交和验收环境准备等阶段不会只在结束后才突然出现。

## 可读性约束

- 需求抽屉扩大到最多 1180px，为六泳道保留足够宽度；窄屏使用横向滚动，不压缩成不可读的小卡片。
- 成功、等待和失败使用不同状态点；角色使用稳定颜色，不直接显示 agent1～agent4。
- “任务执行失败”与“业务评审未通过”使用不同视觉状态；后者明确显示返工方向和评审原因。
- 成功事件摘要最多三行；失败错误默认折叠，展开后错误正文限制高度并独立滚动。
- 原始 Audit Timeline 保留，但默认折叠为“完整审计日志”，泳道负责日常理解，审计日志负责追溯原始事件。
