# 产品需求说明

## 目标

平台为一个组织统一管理多个项目及其 GitHub/GitLab 仓库。每个需求在平台内创建并经历可审计的四 Agent 协作流程，最终形成代码、评审、验收证据和合并记录。

## 角色

| 角色 | 权限摘要 |
| --- | --- |
| 管理员 | 用户、全局配置、Provider、审计与所有项目 |
| 项目负责人 | 项目成员、需求确认、解阻与逐仓合并确认 |
| 开发者 | 创建需求、参与澄清、查看和重新运行被授权任务 |
| 只读成员 | 查看项目、需求、产物和运行历史 |

## 核心需求

1. 项目可绑定多个 GitHub/GitLab 仓库。
2. 一个需求可选择多个仓库和目标分支。
3. 发布需求后，需求澄清者形成结构化规格并等待负责人确认。
4. 系统架构师分析目标仓库并形成跨仓实现方案，等待负责人确认。
5. 开发工程师在隔离工作区实现、测试并生成提交，由可信 Git Worker 推送和创建 PR/MR。
6. 系统架构师以独立只读运行进行 Code Review；阻断问题会退回开发。
7. 验收工程师从干净工作区逐项验证验收标准；失败会退回架构修订。
8. Review 和验收各自最多自动返工三轮，超限进入阻塞。
9. 验收通过后按方案定义顺序逐仓人工确认合并，每次合并后运行组合回归。
10. 全部仓库合并并通过最终组合验收后需求完成。

## 非功能要求

- SQLite 为单机 MVP 权威数据源，Redis 丢失后可以重建任务。
- Agent 沙箱不得获得平台数据库、Docker Socket 或 Git Provider 凭据。
- 所有重要状态、审批、产物版本和外部写操作可审计。
- 默认测试不调用付费模型；真实 DeepSeek 测试必须显式启用。
- 主机除 Docker Desktop 外无需安装项目服务。
- 关键流程必须具备自动化测试和恢复验证。

## MVP 非目标

- 自建 Git 服务、多租户、计费、高可用、跨仓原子合并、邮件/企业微信通知。
